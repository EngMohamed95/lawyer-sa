## القرارات المعمارية

### AD-1 — Custom Claims هي مصدر الحقيقة

```ts
// الـ claim المرفق بكل ID Token
{
  role:     "SUPER_ADMIN" | "LAWYER" | "OFFICE_LAWYER" | "TRAINEE"
          | "PARTNER" | "CONSULTANT" | "SECRETARY" | "ACCOUNTANT" | "CLIENT",
  lawyerId: string,   // معرّف المكتب — نفس اسم الحقل القائم (المبدأ 1)
  plan:     "BASIC" | "PRO" | "PREMIUM",
  status:   "ACTIVE" | "SUSPENDED"
}
```

- تُكتب **حصراً** عبر Admin SDK على الخادم.
- `localStorage` **يبقى** كما هو للعرض السريع (لا حذف — المبدأ 1)، لكنه لم يعد يمنح أي صلاحية فعلية.

### AD-2 — `lawyerId` يبقى اسم حقل العزل

لا نُدخل `tenantId` جديداً. البيانات الحالية تعمل بلا هجرة (المبدأ 7).
المستندات القديمة الفاقدة لـ `lawyerId` تُعالَج بسكربت `backfill` idempotent.

### AD-3 — طريقان للرفع، والقديم يُحصَّن ولا يُحذف

- **جديد (المفضّل):** `POST /api/files/upload` ← Express + multer + Firebase Storage، مسار معزول `tenants/{lawyerId}/…` + Signed URL بصلاحية 15 دقيقة.
- **قديم (يبقى):** `public/upload.php` يُحصَّن بـ: توكن مشترك، قائمة امتدادات بيضاء، حد حجم، `.htaccess` يمنع التنفيذ داخل `uploads/`.
- الشاشات القائمة تُحوَّل تدريجياً إلى المسار الجديد، وكلاهما يعمل طوال فترة الانتقال.

### AD-4 — الذكاء الاصطناعي ينتقل للخادم، والميزة تبقى

تُضاف `POST /api/ai/generate` (مصادَق عليه + محدود المعدل). الواجهة تنادي الخادم بدل Gemini مباشرة.
`sys_aiApiKey` الذي يُدخله المستخدم بنفسه في الإعدادات **يبقى مدعوماً** كخيار "مفتاحي الخاص".

### AD-5 — القواعد تُنشر على مرحلتين

`SHADOW` (تسجيل الرفض بلا منع) ← تحقق 48 ساعة ← `ENFORCE`. لتجنّب كسر شاشة قائمة (المبدأ 7).
